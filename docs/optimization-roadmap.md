# kcode 优化路线与实施清单

> 日期：2026-09-23
> 状态：实施建议，待按任务逐项落地；本文不表示缺陷已经修复。
> 范围：技术架构、Agent 能力、会话可靠性、权限、包边界、CLI 交互与产品路线。
> 依据：当前工作区源码（包含未提交的 B5 改动）、前两轮分析及官方对标资料。

## 1. 决策摘要

下一阶段目标是：**交付可靠、可安装、可恢复、交互顺畅的本地 CLI Beta。**

保留 TypeScript + Node.js + pnpm monorepo、无 IO 的核心循环、daemon + CLI、MCP/Skills 扩展路线。先修状态和执行边界，再完善交互与发布能力，之后进入本地 Web 和远程能力。

推荐推进顺序：

1. 收口失败测试，修复输入丢字和 Hook 否决顺序。
2. 建立单会话运行控制，防止并发请求污染历史。
3. 修复压缩、回退、恢复的一致性，持久化检查点。
4. 收紧权限、插件和系统执行边界。
5. 统一展示状态、输出层级、主题与详情浏览。
6. 完成安装包、跨平台验收和真实仓库评测，发布本地 Beta。
7. 完善子任务与模型适配，再扩展本地 Web、远程和自动化。

暂缓账户、计费、大型插件市场、全量电脑控制以及多前端同时开工。已存在的 E2E 实现保留，远程端到端闭环另行验收。

建议验证的产品定位：**面向中文和 Windows 开发环境，支持自选模型、可恢复长任务的本地编程 Agent。** 这是定位假设，需要真实用户反馈验证。

## 2. 当前状态与证据边界

当前属于功能较完整的开发版。循环、工具、daemon、计划审批、子代理、上下文压缩、回退、MCP、Skills、Hooks 和 TUI 均有实现，但部分状态和错误路径尚未闭环。

前一轮在当前 Windows 环境执行的检查结果：

| 检查 | 结果 | 解释 |
| --- | --- | --- |
| `pnpm typecheck` | 11 个任务通过，部分缓存命中 | 类型基线可用 |
| `pnpm test` | 257 通过、5 失败、1 跳过，共 263 项 | 失败为 Hook 1 项、shell 3 项、DPAPI 1 项 |
| `pnpm lint` | 0 错误、16 警告 | 不代表运行行为正确 |
| `pnpm lint:deps` | 0 错误、10 警告 | 包含过宽规则造成的警告及类型依赖环，需分类 |

Hook 否决后输入仍进入历史是明确逻辑问题。shell 和 DPAPI 失败需要区分代码、终端及当前用户环境因素；不能据此宣称所有正常 Windows 环境都失败。

本次分析未完成真实模型复测、干净机器安装测试、各终端视觉测试或全面安全审计。本文列出的性能指标和产品水平是验收目标，不是已经测得的结果。不同平台只有通过验收才能列为支持平台。

## 3. 对标结论与技术栈决策

| 项目 | 已核对的公开路线或交互 | kcode 应借鉴什么 |
| --- | --- | --- |
| Claude Code | Agent 循环、检查点、转写详情、运行中消息排队 | 获取上下文→执行→验证；低噪声主对话；随时纠偏 |
| OpenCode | TS/Bun、OpenTUI/Solid、多 provider、服务端 API/SDK | 多端共享服务；协议生成；工具详情与思考展示分离 |
| ZCode | 公开 TS/Node/pnpm 工程，桌面/Web/CLI 与共享模块 | 运行时复用、模块边界、完整发行链路 |
| Codex | Rust CLI 路线、App Server 双向协议与审批/schema 机制 | 会话协议、事件与客户端能力协商 |

不能仅凭产品形态推断 Claude Code 的完整内部技术栈，也不能因为采用 daemon 就认定架构优于其他产品。对标用于理解设计，不构成性能或完成率排名。

技术选择：

- **保留 TS/Node。** 当前没有证据表明语言是瓶颈。原生代码仅在沙箱、PTY、进程树和系统凭证等边界按需引入。
- **保留 Ink 做第一轮改造。** 先解决状态、输入和渲染职责，再依据长对话实测判断是否更换框架。
- **保留自有 AgentLoop。** 模型 SDK 负责厂商协议，循环负责任务、工具、权限、预算和恢复；同步修正文档中“不自研 loop”的旧表述。
- **保留 JSONL，先定义正确的事件语义。** 需要索引、并发查询和调度时再引入 SQLite；数据库替换不能修复回放逻辑。
- **扩展模型适配能力。** OpenAI-compatible 不等于各厂商的工具调用、视觉、推理和缓存特性都兼容。
- **本地 Web 优先评估 React + Vite。** 官网和市场确有 SSR/SEO 需求时再使用 Next.js。
- **先优化逻辑模块，不立即扩成大量物理包。** 第二个客户端出现前再提取 client-sdk。

## 4. 优先级定义

- **P0：进入外部 Beta 前必须解决。** 包括数据一致性、输入正确性、运行控制和执行边界；不意味着每项都是已复现的安全漏洞。
- **P1：形成可日常使用、可交付的本地产品。** 包括完整交互、恢复、分发与平台验收。
- **P2：提升效率与扩大产品形态。** 包括增强子任务、代码理解、本地 Web 和远程试点。
- **P3：生态与规模化。** 包括账户、计费、市场运营和复杂电脑控制。

下面按依赖安排 M0–M5。高风险 P0 项不能因为开发顺序靠后而被省略；M0–M3 完成之前不对外宣称可靠 Beta。

### 下一步就执行的任务单

依次提交小改动，每项携带对应回归：

1. **Hook gate 修复**：先让现有失败测试通过，再验证后续轮次不会带入被拒绝文本。
2. **输入正确性修复**：去掉吞键启发式的默认路径，补中文+数字、混输、粘贴测试及目标终端人工验证。

4. **M1 验收用例**：先记录“自动压缩、手动压缩、回退后恢复”的预期行为，作为下一轮修复的依据。

M0 完成后是“输入和运行控制更可靠的开发版”，尚不是可恢复 Beta。

## 6. M1：会话、压缩与回退一致性

依赖：M0 的运行互斥和终态定义。

| ID | 优先级 | 当前问题及实施内容 | 验收标准 |
| --- | --- | --- | --- |
| M1-01 | P0 | 回放目前只追加压缩摘要；定义覆盖范围、保留轮次和锚点，统一状态归约 | 在线有效历史与重放后的有效历史一致 |
| M1-02 | P0 | 手动压缩和 rewind 缺完整持久化；为其写入可恢复事件或分支记录 | 重启不复活已回退内容，不丢失压缩结果 |
| M1-03 | P0 | 固定消息数切片可能拆开工具调用/结果；按完整轮次和调用组压缩 | 无孤立 tool result；8–10 条短历史边界行为正确 |
| M1-04 | P1 | 检查点索引目前仅在内存且关闭清理；持久化清单、前像、后像 hash | 重启后可列出可用检查点；外部修改冲突不会被无提示覆盖 |
| M1-05 | P1 | 会话绑定 workspaceId、parent/branch 信息、模型及附件引用 | latest 默认在当前项目选取；恢复来源明确；缺附件可诊断 |
| M1-06 | P1 | 明确日志尾部损坏、未完成调用、事件版本迁移和落盘失败行为 | 崩溃后能恢复有效前缀；不会自动重复执行不确定的写入动作 |
| M1-07 | P1 | 用持久化 SessionManager 替代连接拥有会话；加入 attach 和事件游标 | CLI 断线不销毁可恢复会话；重连无重复执行、无重复展示 |

建议区分：workspace、session、run、event、toolCall、checkpoint；事件拥有稳定 ID/序号。对语义变更增加版本或显式迁移，保留旧会话兼容测试。

JSONL 作为事件来源时，先完成可靠追加，再向客户端宣布持久化成功。stream delta 可临时展示，但必须明确其与持久化消息的关系。

检查点只对覆盖范围作承诺。shell 或外部进程修改不能因存在 write/edit 快照而宣称全部可回滚。

入口：`packages/runtime/src/session/`、`packages/core/src/context/compact.ts`、`apps/daemon/src/checkpoints.ts`、`apps/daemon/src/composition.ts`。

M1 完成后可达到“单机任务可中断、断线重连与恢复结果可验证”的水平，尚需权限和发布验收。

## 8. M3：交互与分发，形成 CLI Beta

展示设计可提前准备；运行中排队、恢复和审批交互依赖 M0–M2 的真实状态。

### 8.1 输出层级

| 层级 | 内容 | 默认展示 |
| --- | --- | --- |
| 正文 | 对用户的解释、进展、结论、问题 | 清晰可见 |
| 工作状态 | 搜索、编辑、测试、限流重试、等待批准、取消 | 一行稳定状态，事件驱动 |
| 执行记录 | 工具、目标、结果、耗时 | 摘要，可进入详情 |
| 模型思考摘要 | provider 实际提供的可展示内容 | 独立开关，默认折叠 |

不从等待时间推断模型在做什么，不生成伪造思考。显示思考摘要与模型推理强度是不同设置。失败关键内容应可见；成功的重复读取/搜索可以合并。

### 8.3 字体、排版与颜色规则

CLI 继承终端字体、字号、行距，应用主要负责颜色、粗体、留白、缩进与宽度。字体配置指南可提供建议，但不擅自修改用户终端。

- 正文继承终端前景色，去掉固定白色；标题用粗体和少量强调色。
- 用户消息保持足够对比度，不默认整段 dim。
- 思考摘要展开后采用正常可读文字，不使用大段低对比斜体。
- 错误和 diff 同时使用文字/符号与颜色，不能只靠红绿区分。
- 按显示宽度截断；窄屏表格退化为纵向信息；代码复制不混入装饰字符。
- 欢迎页首次详细，后续简洁；状态栏优先显示项目、模式、模型、任务状态。
- 用户浏览历史时不强制跳到最新位置，显示有新输出的提示。

### 8.4 建议布局

```text
kcode · 当前项目/分支 · 编辑需确认 · 当前模型

› 修复登录失败的问题

正在检查登录流程和相关测试。

✓ 搜索与阅读 · 6 个文件
✓ 修改 src/auth.ts                         +12 -4
  运行登录测试…                            8s

────────────────────────────────────────────
› 补充：需要兼容旧版 token
  Enter 排队发送 · Esc 停止当前任务
────────────────────────────────────────────
执行中 · 2 个文件已修改 · 详情 Ctrl+O
```

展示入口必须有实际可用的命令/快捷键，不能用不可操作的文字伪装按钮。

### 8.5 体验验收

至少覆盖 Windows Terminal + PowerShell/Git Bash，以及 Linux 终端；若承诺 macOS，再加入 macOS 验收。

- 混输：`版本2`、`修复3处`、英文变量名接中文、emoji、组合字符、多行粘贴。
- 布局：80/120 列，运行中缩放，深色/浅色，宽表格、未闭合代码块。
- 长任务：大日志、查历史时新内容到达、审批中断、网络重试、断线恢复。
- 性能目标：目标机器输入回显 P95 < 100ms；取消请求 200ms 内显示反馈（不等于进程已退出）；历史不重复打印。
- 默认测试不以真实模型响应时间衡量 TUI；输入、渲染与网络延迟分别记录。

M3 完成并通过 M0–M2 门禁后，可达到可安装、可日常使用的本地 CLI Beta。

| M4-01 | P1 | 模型能力注册表与原生适配；窗口、输出预留、视觉、缓存、usage | 用真实 provider 测试确认；不只按模型名称正则猜能力 |
| M4-02 | P1 | 子任务持久化、父子 run 关联、用量汇总、取消传播和文件改动归属 | 子任务修改可追溯；费用不只停留在返回文本；支持受限并发 |
| M4-03 | P1 | AGENTS.md 目录作用域、Skills 加载策略与项目隔离 | 指令优先级明确，子任务所需项目规则不丢失 |
| M4-04 | P2 | LSP 诊断、符号/引用定位、Git/worktree 工作流 | 真实多文件任务证明收益后再扩大范围 |
| M4-05 | P2 | 历史搜索、外部编辑器、导出和快捷键配置 | 提升高频任务效率，终端冲突有替代入口 |
| M5-01 | P2 | 提取 client-sdk，接入本地 Web | 两个客户端共享同一服务与会话状态，不重复实现业务 |
| M5-02 | P2 | 远程配对、授权、撤销、E2E 与断线恢复闭环 | 完整故障/撤销验收后才开放远程执行 |
| M5-03 | P2 | 有范围预授权的本地调度 | 任务持久化；无人值守 ask→deny；重启不重复执行 |
| M5-04 | P3 | 账户、计费、市场、签名分发、电脑控制 | 由真实用户需求和前序稳定性决定投入，不预先全量建设 |

已有 task 工具不能直接视为并行多 Agent 平台：当前 task 为非只读工具，循环只对全只读工具批次并行；子任务事件/审计在内存，父任务回退关联也需要补齐。

## 10. 包模块调整

保留现有物理包，按业务变化逐步迁移。每次功能修复只做所需的职责提取，避免先进行全仓大重构。

| 位置 | 目标职责 | 调整 |
| --- | --- | --- |
| contracts | 协议 DTO、事件 schema、共享类型 | 与进程内 ports 区分，不继续堆远期云协议 |
| core | 循环、上下文策略、执行管线 | 保持无 IO；测试工具使用独立 testing 导出 |
| runtime | SessionRunner、状态归约、日志、恢复、检查点、子任务生命周期 | 承接 daemon 中可复用的会话业务 |
| tools | 文件、命令、搜索和网页执行器 | 通过受控端口调用系统能力 |
| extensions | Skills、Hooks、插件与 MCP 适配 | MCP 归属调整可后置，不阻塞可靠性修复 |
| platform | provider、凭证、系统执行后端 | 先内部划分 providers/credentials/sandbox |
| apps/daemon | 入口、组合根、RPC、连接与订阅 | handler 不承担会话业务实现 |
| apps/cli | CLI 命令、TUI、客户端适配 | 展示层不直接调用 provider/凭证实现 |
| 未来 client-sdk | 类型化请求、事件订阅、重连、协议协商 | 第二个客户端启动前提取 |

TUI 建议拆为 `theme/`、`terminal/`、`state/`、`transcript/`、`input/`、`dialogs/`、`status/`。重点拆分约 2060 行的 App.tsx；行数只是定位职责集中度的信号，不作为机械拆分目标。

依赖门禁：允许 CLI 使用 contracts/client-sdk；禁止 TUI 依赖 platform 实现；core 到 IO 实现和实际运行时循环设为 error；类型环单独判断，避免一刀切。

## 11. 评测与发布门槛

现有 mini-shop 10 任务可保留为冒烟基线，不能据此推断通用代码修改能力。

建议第一批真实基准覆盖：单文件修复、多文件重构、测试失败定位、长上下文续接、权限拒绝、取消、压缩后恢复、回退后恢复、Windows shell 和安装包首跑。

固定任务、仓库初始状态、模型配置和预算；每类任务重复运行并保存轨迹。记录：

- 最终功能正确率与回归情况。
- 用户干预次数、完成耗时、token/成本。
- 重试、取消、恢复成功情况。
- 首次安装到首个成功任务的步骤和失败点。
- UI 输入延迟、渲染异常、日志可查性。

外部 Beta 发布门槛：P0 全部关闭；目标平台类型/测试/构建/安装检查通过；无未解释阻断；权限能力声明准确；关键恢复矩阵通过；真实模型评测结果可追溯。

## 12. 各阶段实现后能达到什么程度

| 完成范围 | 可承诺的水平 | 仍不应承诺 |
| --- | --- | --- |
| M0 | 输入不丢字、拒绝有效、同会话串行、取消反馈清楚的开发版 | 长任务恢复可靠、可对外稳定分发 |
| M0–M1 | 有可验证恢复语义的单机 Agent；重连和回退有依据 | 完整沙箱与跨平台安装成熟 |
| M0–M3 | 可安装、可日常使用、状态清楚的本地 CLI Beta | 全面达到 Claude Code/OpenCode 的质量与生态 |
| 加 M4 | 多模型、子任务、项目上下文和工程工作流更完善 | 不经基准就宣布达到或超过竞品 |
| 加 M5 前三项 | 共享会话的多端 Agent 与受控远程/自动化能力 | 成熟商业平台、完整企业认证和大规模市场生态 |

这是按验收通过后的能力边界描述，不是进度百分比或工期承诺。研发工期取决于人数、每周投入、平台覆盖与 OS 沙箱方案；先完成 M0/M1 后再据实估算后续阶段。
